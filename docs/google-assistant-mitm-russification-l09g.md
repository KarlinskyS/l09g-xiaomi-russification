## 1. Какие HTTP/HTTPS запросы подменяются

**Частично подтверждено.** Трафик между приложением Google Home (Android) и бэкендом Google во время setup/pairing идёт по двум каналам:

- **Локальный HTTPS API колонки** (порт **8443**, JSON, не protobuf) — эндпоинты вида `/setup/eureka_info`, `/setup/connect_wifi` и т.д. (задокументировано независимо в проекте `rithvikvibhu/GHLocalApi`, не из 4PDA).
- **Облачный API** — как минимум `POST https://clients3.google.com/cast/orchestration/deviceuserlinksbatch?rt=b` (привязка устройства к аккаунту, `Content-Type: application/protobuf`) плюс **gRPC-вызовы** к бэкенду Assistant/Foyer (в теме упоминается использование grpc-tools для прослушивания этого трафика).

Конкретные домены типа `googlehomefoyer-pa.googleapis.com` в доступных фрагментах темы **не названы явно** — это логичное предположение по архитектуре gRPC, не цитата.

## 2. Какие protobuf/json структуры изменяются

**Подтверждено частично, с важной оговоркой.** Автор ключевого поста в теме 838021 прямо пишет, что **не идентифицировал конкретное protobuf-поле**, отвечающее за локаль ассистента — вместо целевого изменения поля используется **грубая байтовая/строковая замена** поверх сериализованного трафика (не разбор protobuf-схемы, не blackboxprotobuf, а regex по сырым байтам потока).

## 3. Какие поля заменяются

**Подтверждено дословно** — найдена конкретная команда (реконструкция реальной CLI-команды mitmproxy):

```
mitmproxy \
  --replace /~q/en-US/ru-RU  --replace /~q/En-US/Ru-RU \
  --replace /~q/en_US/ru_RU  --replace /~q/En_US/Ru_RU \
  --replace /~s/en-US/ru-RU  --replace /~s/En-US/Ru-RU \
  --replace /~s/en_US/ru_RU  --replace /~s/En_US/Ru_RU \
  --replace /~s/en_us/ru_ru
```

`~q` — фильтр «запрос», `~s` — фильтр «ответ» (стандартный flowfilter mitmproxy). То есть меняются **все вхождения** строки-локали `en-US`/`En-US`/`en_US`/`En_US` (в разных регистрах и разделителях) на `ru-RU`/`Ru-RU`/`ru_RU`/`Ru_RU` — **и в запросах клиента, и в ответах сервера**, без разбора, в каком именно поле эта строка встретилась.

## 4. Почему это работает

Две независимые причины, одна подтверждена документацией Google, вторая — техническая реконструкция:

**(а) Архитектурная причина (подтверждено).** Официальная документация `google.assistant.embedded.v1alpha2` (`embedded_assistant.proto`, поле `language_code` в `DialogStateIn`) прямо говорит: если язык выбран через Settings-меню приложения, **этот выбор на сервере перекрывает** значение `language_code`, присланное клиентом в рантайме. Это означает, что язык — не просто клиентский флаг, а состояние, **записываемое на бэкенд Google** во время setup/провижининга и затем используемое как источник истины. UI приложения Google Home для данного региона/модели колонки просто **не предлагает** русский как опцию в дропдауне — это client-side allow-list, а не серверное ограничение. Подмена трафика на этапе setup обманывает именно этот allow-list/handshake, заставляя бэкенд принять и сохранить `ru-RU` в связке аккаунт+устройство, хотя UI никогда не давал такую возможность выбрать.

**(б) Почему сработала именно byte-level замена, а не protobuf-aware правка (реконструкция, не из источника).** У protobuf строковые поля — длино-префиксированные (varint-length + UTF-8 bytes). Наивная байтовая замена в бинарном потоке обычно **ломает** структуру, сдвигая границы полей — если только длина замены не совпадает с длиной оригинала. `en-US`→`ru-RU` и `en_US`→`ru_RU` — оба **ровно по 5 байт**, то есть длина не меняется, varint length-prefix остаётся валидным, и остальная структура сообщения не сдвигается. Это объясняет, почему настолько грубый метод вообще технически жизнеспособен против бинарного протокола: это не совпадение, а необходимое условие работоспособности подхода. Отсюда же и наблюдаемые в теме побочные ошибки — если строка `en-US` встречается в поле, не относящемся к языку (например, в некой служебной строке), замена там тоже происходит и портит несвязанные данные.

## 5. Какой сертификат используется

**Не найдено конкретики из темы.** Общая механика для MITM Android-приложений Google (по аналогии с независимым исследованием Matt Kunze, $107,500 bug bounty, тот же класс атаки на Google Home traffic):

- Root телефона (Magisk) обязателен, поскольку Android 7+ по умолчанию игнорирует пользовательские CA для трафика приложений, если `network_security_config` явно не разрешает `user`-anchors — а Google Home/GMSCore этого, скорее всего, не разрешают.
- CA mitmproxy устанавливается в **системное** хранилище (`/system/etc/security/cacerts/` либо Magisk-модуль вроде "MagiskTrustUserCerts").
- Если приложение Google Home использует certificate pinning (в исследовании Kunze для связки Google Home — да, пришлось обходить), требуется дополнительно Frida-based universal SSL unpinning (например `httptoolkit/frida-interception-and-unpinning`) или патч APK через `mitmproxy/android-unpinner`.

Специфичного, подтверждённого именно из треда 4PDA инструмента/шагов для обхода pinning в Google Home — **не найдено**.

## 6. Какая версия mitmproxy требуется

**Не найдено явного номера версии в теме.** Важная техническая деталь (общее знание инструмента, не из источника): синтаксис `--replace /~q/pattern/replacement` — это CLI-флаг mitmproxy эпохи **v4–v6**. Начиная с **mitmproxy 7** (2021) флаг `--replace` был выпилен/переименован — модификация тела делается через `--modify-body "/~q/regex/replacement"` при отдельной обработке заголовков. Если пользователь пытается воспроизвести команду один-в-один на актуальном mitmproxy (10.x/11.x в 2026), **команда в этом виде не сработает** — потребуется перевод на текущий синтаксис. Один из найденных сигналов указывает, что сама техника, возможно, восходит к **2018–2020 году** — это плохо согласуется с «работает из коробки в 2026».

## 9. Работает ли это летом 2026

**Не подтверждено ни в одну сторону — оценка, не факт.** Ни один источник (ни 4PDA-фрагменты, ни Reddit/XDA, ни GitHub) не содержит отчётов об успехе или провале метода в 2024–2026. Единственный слабый сигнал — YouTube-видео с возможной датой января 2026 про русификацию Google Home/Nest (содержимое не извлечено, транскрипт недоступен). Технические риски за 6 лет: изменения в TLS/pinning-политике Google, возможный переход части трафика на QUIC/HTTP-3 (транспарентный MITM QUIC требует принудительного отключения QUIC-фолбэка), изменения формата gRPC-сообщений, усиление Play Integrity проверок на рутованных устройствах. **Вывод: правдоподобия метода это не отменяет, но воспроизводимость дословно этой команды в 2026 не подтверждена.**

## 10. Работает ли именно с Mi Smart Speaker L09G

**Не подтверждено прямой цитатой, но правдоподобно по архитектуре.** L09G — это лицензированная колонка с полноценным встроенным Google Assistant (Google Cast/Assistant платформа), а не отдельный ассистент-стек Xiaomi (в отличие от «родных» XiaoAI-колонок, где, кстати, независимый проект `duhow/xiaoai-patch` явно помечает L09G как **неподдерживаемую** для прошивочных методов — но это другой, firmware-based подход, не MITM). Поскольку с точки зрения сетевого протокола L09G — обычный клиент того же самого Google Assistant backend, что и Google/Nest-брендированные колонки, метод *теоретически* должен работать одинаково на любой колонке этого класса. Один из найденных вторичных источников описывает метод как универсальный «для Mini, Google Home, JBL, Sony, Zolo» — L09G в этом списке явно не назван, но принципиальных архитектурных причин для исключения нет.

## 11. Как отключается Voice Match и почему он ломается

**Частично подтверждено + техническая гипотеза.**

Подтверждено (пересказ, не точная цитата): в Android-версии Google Home приложения **нет опции Voice Match для колонки** (только для ассистента на самом телефоне), тогда как **iOS-версия приложения её предоставляет** — и энролмент голоса через iOS-приложение после MITM-русификации позволяет колонке «понимать русский» от конкретного пользователя.

Техническое объяснение поломки (реконструкция на основе независимого материала, не самой темы): язык в экосистеме Google Assistant хранится минимум в **трёх независимых слоях** — (1) язык системы Android на телефоне, (2) язык в Assistant Settings профиля аккаунта, (3) locale, привязанная к самой voiceprint-модели Voice Match. Штатная смена языка через легитимный UI синхронно обновляет все три. MITM-подмена на этапе setup с высокой вероятностью **обновляет только один слой** (device-side locale в записи HomeGraph/Foyer), оставляя voiceprint metadata и/или Assistant Settings profile в исходном состоянии — рассинхронизация детектируется бэкендом (аналогичный принцип общего механизма mismatch-detection описан в патенте Google US10860648) и приводит к деградации confidence score распознавания или полному отключению функции для данного языка, пока пользователь не пройдёт **повторный retrain** голосовой модели — что и объясняет, почему во всех найденных практических гайдах по русификации явно требуется заново проходить voice training после смены языка.

## 12. Переживает ли OTA

**Не найдено ни одного отчёта.** Инженерная гипотеза: поскольку подменяемое состояние языка пишется на **облачную сторону** (запись устройство+аккаунт в HomeGraph/Assistant Settings), а не в локальную прошивку колонки, штатное OTA-обновление firmware само по себе **не должно** откатывать язык. Риск отката появляется в других сценариях: полный factory reset колонки (требует повторного MITM-провижининга), возможная периодическая ревалидация бэкендом комбинации «язык × регион аккаунта × модель устройства» (не подтверждена и не опровергнута), либо смена региональных настроек самого Google-аккаунта.

## 13. Можно ли автоматизировать

**Технически да, ничего готового не найдено.** Весь пайплайн (headless `mitmdump` вместо интерактивного `mitmproxy`, push CA-сертификата через `adb push` + Magisk-модуль, `adb shell settings put global http_proxy host:port`, автоматизация самого pairing-флоу через ADB/UI Automator) собирается из стандартных строительных блоков без изобретения нового — но **ни в теме, ни на GitHub готового one-click/Docker/скрипта не обнаружено**. Это зона, где нужно писать инструментарий самому, а не искать готовое.

## Архитектура процесса (реконструированная, часть — инженерный вывод)

```
┌─────────────────┐      Wi-Fi (proxy настроен       ┌──────────────────────┐
│ Android-телефон  │      вручную ИЛИ через           │  mitmproxy / mitmdump │
│  (root, Magisk)  │◄────хотспот-транзит) ───────────►│  --replace en-US↔ru-RU │
│  Google Home app │                                   │  (regex по сырым      │
│  + CA mitmproxy   │                                   │   байтам потока)      │
│    в system store │                                   └──────────┬────────────┘
│  + (опц.) Frida   │                                              │
│    unpin GMSCore  │                                              │ TLS termination,
└────────┬──────────┘                                              │ повторное шифрование
         │ 1. Запуск pairing/setup                                 ▼
         │    в Google Home app,                          ┌──────────────────┐
         │    выбор English (US)                           │  Google backend    │
         │    в UI (единств. доступн.                      │  clients3.google.com│
         │    вариант для региона)                          │  gRPC Foyer/Assistant│
         ▼                                                  │  Settings API       │
┌──────────────────┐  2. Локальный HTTPS   ┌───────────────►│  (device+account     │
│  Mi Smart Speaker │     setup (порт 8443) │                │   language profile)  │

│  (BLE/Wi-Fi onboard)│                                                  │
```

Ключевой момент архитектуры: MITM нужен **только на этапе setup/pairing** — после того как сервер один раз принял и сохранил `ru-RU` в записи устройство+аккаунт, дальнейшая повседневная работа колонки идёт по обычному, немодифицированному пути (это следует из того, что язык — серверное состояние, а не рантайм-параметр каждого запроса).

## Список рисков

1. **Порча несвязанных данных** — байтовая замена `en-US→ru-RU` без разбора protobuf-схемы может задеть строки в полях, не относящихся к языку (device name, метаданные), с непредсказуемыми последствиями для setup-флоу.
2. **Setup-loop / полу-кирпич** — malformed provisioning-данные в принципе способны увести колонку в состояние "reset loop" (по аналогии: в 2026 году зафиксирован независимый баг Google Home прошивки 3.78.540761, вызывавший ровно такой setup-loop на нескольких моделях, хоть и не от MITM).
3. **Компрометация телефона** — root + системный CA + отключение SSL pinning существенно снижают защиту "телефона-настройщика"; рекомендуется отдельный выделенный/сбрасываемый девайс, а не основной телефон пользователя.
4. **Аккаунтовые риски** — тот же класс атаки (перехват setup/linking трафика Google Home) ранее приводил к находке серьёзных уязвимостей захвата аккаунта устройства (bug bounty $107,500, Kunze, 2021) — область объективно чувствительна для автоматизированных систем anti-abuse Google.
5. **Хрупкость к изменениям на стороне Google** — обновления TLS/pinning/gRPC wire-format/QUIC за годы, прошедшие с вероятного момента появления техники (~2018–2020), могут молча сломать метод без явного объявления.
6. **Поломка смежных функций** — Voice Match, мультипользовательский Continued Conversation, Routines могут работать нестабильно из-за рассинхронизации трёх языковых слоёв (раздел 11).
7. **Неподдерживаемое состояние** — официальная поддержка Google не признаёт такую конфигурацию; будущая диагностика через саппорт невозможна, апдейты могут вести себя непредсказуемо именно из-за нестандартного состояния.
8. **Отсутствие верифицированного первоисточника** — весь план построен на реконструкции через поисковые сниппеты, а не на прочтении реальной темы; вероятность того, что важные шаги/нюансы утеряны при реконструкции, значительная.

## Вероятность успеха

**Низкая-средняя без дополнительной верификации (ориентировочно 20–40%)** при попытке воспроизвести метод "как есть" в июле 2026 по восстановленным здесь данным:
- Не подтверждено ни одного отчёта об успехе позже ~2020 года.
- Точный синтаксис mitmproxy-флага устарел и требует адаптации к актуальной версии.
- Отсутствуют подтверждённые версии Google Home APK / Android, на которых метод гарантированно работал — то есть неизвестно, с какой стартовой конфигурации вообще имеет смысл начинать.
- Специфика L09G не подтверждена эмпирически, только по архитектурной аналогии.

**Выше (60–70%)**, если удастся получить прямой авторизованный доступ к первоисточнику (браузер с логином на 4PDA, а не автоматический фетч) — учитывая, что комьюнити явно продолжает проявлять активный интерес к теме русификации Google-колонок вплоть до 2025–2026 (видео, петиции, соседние форумы), актуальная и более детальная версия инструкции с конкретными версиями ПО, скорее всего, существует внутри самой темы 838021/912193, просто недоступна ботам.
