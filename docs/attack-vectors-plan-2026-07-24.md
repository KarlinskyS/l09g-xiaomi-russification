## 0. Ключевое переосмысление: мы били не в тот слой

Все 4 подхода прошлой сессии боролись с **клиентским allowlist языков в приложении** (`koo.A(int)` → `bnrv`/`bnjh`, Phenotype-флаги `45356207 / 45356208 / 45356708`, ни в одном нет `ru-RU`). Гипотеза была: «разблокируем список в UI → русский станет доступен».

Чтение кода показывает, что это **не главный гейт**. Полный путь языка при онбординге (`DeviceSetupActivity` + `ahtq` + `akek`):

1. `akek.d()` = `e(Locale.getDefault())` → строка вида `"ru-RU"`, берётся **из системной локали телефона**, а не из аккаунта/структуры (`akek.java:34-39`).
2. `av.h = akek.d()` — язык телефона пишется в объект устройства **безусловно** (`DeviceSetupActivity.java:911, 1088`).
3. Экран выбора языка (`wbr`) показывается **только если** `bw()` вернёт true:
   ```java
   private final boolean bw() {                              // DeviceSetupActivity:522
       return lM().u && !koo.B(akek.d(), lM().h().ae);
   }
   ```
   - `lM().u` — булев флаг «модель требует явного выбора языка» (`ahtq.u`, приходит от устройства/модели).
   - `koo.B("ru-RU", ae)` — есть ли локаль телефона в клиентском allowlist. Для `ru-RU` → false.
   - Если `lM().u == false` → `bw()` = false → **экран языка вообще не показывается, язык молча берётся из `Locale.getDefault()`**.
4. Далее — **настоящий гейт** (`DeviceSetupActivity.java:742`):
   ```java
   this.av.d(3, lM().e(str2, str2.split("-")[0]));   // str2 = av.h, напр. "ru-RU" → e("ru-RU","ru")
   ```
   `ahtq.e(str, str2)` (`ahtq.java:795-818`) перебирает `this.bn` — **список локалей, который прислала САМА колонка**, и возвращает `ahte`, только если найдёт `.a == "ru-RU"` или `.a == "ru"`. Иначе **`null`**.
5. `ahtq.bn` наполняется из `GET https://<ip>:8443/setup/supported_locales` (`ajik.java`, парсинг `ajkd.b(JSONArray)` → `ArrayList<ahte>`; поле `ahtq.bn`, `ahtq.java:131,305`).

**Вывод:** даже если полностью обойти клиентский allowlist приложения и подсунуть `av.h="ru-RU"`, метод `e()` сверит его со списком локалей **прошивки колонки**. Нет `ru`/`ru-RU` в прошивке → `null` → язык не проставится. Приложение — вторичный гейт. Первичный — **прошивка устройства + серверный профиль**.

Это ровно тот «трёхслойный» барьер, который предсказывал MITM-документ, только теперь он локализован в конкретном коде.

## 1. ГЛАВНЫЙ невыполненный эксперимент (делать первым, до всего)

**Запросить у самой колонки её список поддерживаемых локалей.** За 4 сессии это ни разу не сделано, а именно этот ответ определяет всю стратегию.

```
GET https://<speaker-ip>:8443/setup/supported_locales
GET https://<speaker-ip>:8443/setup/eureka_info   (поля locale, country_code — что стоит сейчас)
```

Колонка отвечает по локальному API (самоподписанный TLS, `--insecure`/curl `-k`; авторизация LAT может не требоваться для read-эндпоинтов, проверить). Инструментарий для доступа к устройству у нас уже есть.

Две ветки исхода — они взаимоисключающие и задают всё остальное:

- **Ветка A: в ответе есть `ru`/`ru-RU`.** Тогда прошивка русский умеет, и вся проблема — только в клиентском UI приложения. Достаточно провести `"ru-RU"` в `av.h` → работают дешёвые вектора §2 (в первую очередь просто **сменить системную локаль телефона на русскую**). Вероятность успеха высокая.
- **Ветка B: `ru` в ответе нет.** Никакой трюк на стороне приложения не поможет — `e()` всегда вернёт `null`. Русский надо *добавить в прошивку колонки* или *заставить бэкенд провижинить ru на устройство*. Это тяжёлые вектора §4/§5. Вероятность — R&D-уровень.

> Пока эта команда не выполнена, продолжать возню с Frida-хуком `knf.v` (подход №4 прошлой сессии) — потенциально трата времени: он чинит вторичный гейт, не проверив первичный.

Дополнительно на этом же шаге снять: `GET /setup/offer`, весь `eureka_info` целиком (там `public_key`, `certificate`, `model_name`, `cast_build_revision` — версия прошивки, пригодится для §4).

## 2. Вектора при Ветке A (прошивка умеет русский) — дёшево

### 2.1. Системная локаль телефона = русский (НИКОГДА НЕ ПРОБОВАЛИ) ★ приоритет
Самый недооценённый вектор. `av.h` берётся из `Locale.getDefault()`. Если телефон целиком в русской локали:
- `akek.d()` → `"ru-RU"` автоматически, без всяких хуков.
- Если `lM().u == false` (модель не требует выбора) → экран языка не показывается, `"ru-RU"` уходит как есть.
- Если `lM().u == true` → покажется экран выбора без ru; но тогда достаточно локально добавить ru в allowlist (§2.2), и он там появится «легально».

**RE до попытки:** узнать значение `lM().u` для L09G. Оно приходит в `ahtq` — проверить, откуда именно (из модели `akdv`/из ответа устройства). Если `u==false` — вектор тривиален и не требует ни root-хаков, ни патчей вообще, только сменить язык телефона и пройти онбординг заново.

Телефон уже `dipper`/MIUI — можно временно переключить систему на `ru-RU`.

### 2.2. Патч кэша Phenotype-флагов в SharedPrefs приложения (вместо Frida) ★
Прошлая сессия хукала `koo.A`/`knf.v` в рантайме через Frida (хрупко, слетает при перезапуске процесса, привязано к обфусцированным именам конкретного билда). Но значения флагов `45356207/08/708` **кэшируются на диске** в SharedPrefs приложения (`sharedPrefs_ph`, лог-тег `PhenotypeFlag`; onboarding-report §7 прямо отмечает «кэшируется в SharedPrefs и не обязательно перезапрашивается»).

Под root можно **отредактировать XML SharedPrefs напрямую** в data-каталоге `com.google.android.apps.chromecast.app`, дописав `,ru-RU` в закэшированное значение флага. Плюсы против Frida:
- Не зависит от обфусцированных имён (`knf.v` меняется каждый билд) — правим данные, не код.
- Переживает перезапуск процесса (то, на чём сломался подход №4).
- Не трогает подпись APK → GMS-доверие цело (в отличие от подхода №3).

**RE до попытки:** найти точный файл/ключ, где лежит закэшированное строковое значение флага (`find /data/data/.../shared_prefs -name '*ph*'`, грепнуть по CSV локалей). Проверить, читается ли значение из кэша или дёргается с сервера при каждом онбординге (если второе — отключить сеть GMS на момент чтения, чтобы взять дефолт/кэш).

Это по сути **та же цель, что подход №4, но надёжным способом.** При Ветке A может оказаться достаточным.

### 2.3. Phenotype override через GServices, а не broadcast
Подход №3 прошлой сессии пробовал `FLAG_OVERRIDE` broadcast → отбит проверкой подписи вызывающего. Но onboarding-report §7 (`anwc.java:42`, «Cannot set GServices prefix and skip GServices») показывает: у флагов есть **второй путь получения значения — GServices**. GServices-таблица (`com.google.android.gsf`/`settings`-провайдер) под root пишется напрямую (`am`/`content insert`/правка БД), без broadcast и, возможно, без той signature-проверки, что убила broadcast-путь.

**RE:** установить точный GServices-ключ для этих флагов и приоритет (override-таблица Phenotype vs серверная синхронизация). Средняя перспективность, но дёшево проверить.

## 3. Серверные/аккаунтные вектора (легальные, не трогают устройство) — пробовать параллельно с §1

Ни один не пробован. Все — обычные настройки, не «хаки», риск минимальный.

### 3.1. Регион+язык Google-аккаунта = Россия/русский
Сменить в аккаунте Google: язык интерфейса → русский, **регион/страна** → Россия. Бэкенд Assistant частично гейтит доступность языков по региону аккаунта (петиция change.org подтверждает, что ограничение регионально-модельное). Возможно, после смены региона UI начнёт предлагать ru для устройства нативно. Полностью обратимо.

### 3.2. Assistant как второй язык профиля
Google Assistant поддерживает до 2 языков одновременно на аккаунт. Если через Assistant settings (веб/приложение) удастся добавить русский как *второй* язык ассистента аккаунта — устройство наследует языки профиля. Проверить, доступен ли ru в дропдропе Assistant-настроек (это отдельный список от setup-allowlist колонки).

### 3.3. iOS-приложение Google Home
MITM-документ (§11) прямо отмечает: **iOS-версия приложения показывает опции (в т.ч. Voice Match для колонок), которых нет в Android-версии**. Не исключено, что iOS-клиент и языковой allowlist имеет другой/более широкий. Если есть доступ к iPhone/iPad — пройти онбординг (или смену языка уже привязанной колонки) через iOS-приложение и посмотреть, есть ли там ru. Дёшево, если железо есть.

### 3.4. Веб-консоль / смена языка уже привязанного устройства
Проверить, можно ли сменить язык **уже настроенной** колонки (не в онбординге, а в настройках устройства в приложении/на home.google.com). Путь через настройки может дёргать другой эндпоинт с другим (серверным) списком языков, чем клиентский setup-allowlist.

## 4. Вектора при Ветке B (прошивка НЕ умеет русский) — тяжёлые, R&D

Если `supported_locales` колонки не содержит ru — гейт в прошивке/на сервере, приложение бессильно. Порядок по перспективности:

### 4.1. Заставить бэкенд провижинить ru на устройство (MITM, но прицельно)
Не «слепая байтовая замена en-US→ru-RU» из подхода №1 (она не сработала — нужный запрос не ловился), а:
- Сначала **verbose-лог всех путей и тел** к allowlist-доменам при онбординге (рекомендация №3 прошлой сессии) — построить полную карту, какой эндпоинт реально несёт локаль/список локалей.
- Особый интерес — **ответ `GET /setup/supported_locales` от устройства**: если подменить в MITM *ответ колонки*, дописав `ru-RU` в JSON-массив, то `ahtq.bn` в приложении получит ru, `e()` перестанет возвращать null. Это подмена **локального** канала (порт 8443), а не облачного — мы её уже умеем перехватывать (ssl_insecure-фикс из подхода №1). **Но:** это обманет только приложение; реально ли колонка заговорит по-русски, зависит от того, тянет ли её собственный ассистент-стек ru с сервера. Проверяемо эмпирически.
- Облачный канал: `deviceuserlinksbatch` (`clients3.google.com`) и gRPC Foyer — найти, где сервер отдаёт «доступные для устройства языки», и подменить *ответ*.

### 4.2. Firmware-патч через UART/U-Boot (teardown-doc)
Физический доступ, не зависит от Google. Из teardown: 3-pin UART (115200), U-Boot 2015.01 с полным набором команд, `bootdelay=1`, partition layout известен. Путь по аналогии с `duhow/xiaoai-patch`:
- Дамп `boot`/`recovery`/`system`/`chrome` разделов через `nand`/`md.b`.
- Раздел `chrome` (самый крупный) — почти наверняка Cast/Assistant-стек Google; там же, вероятно, живут ресурсы локалей.
- Найти, где прошивка формирует свой `supported_locales`, дописать ru, перепаковать, записать назад.
- **Кандидат №1 для быстрой проверки:** `factory_mode=1` через U-Boot env — на других Xiaomi открывает adb/root на этапе загрузки (не проверено на L09G).

Риск: заблокированный bootloader + возможная verified-boot на самой колонке (в отличие от телефона — не проверено). Готового рецепта под L09G в паблике нет — это R&D с нуля, но партиции задокументированы.

### 4.3. Прямая запись локали в устройство через local API / BLE
- `POST /setup/set_eureka_info` пишет поля на устройство, среди них **`locale`** (`ahtq.java:642`, `ak(arrayList,"locale", ...)`). Попробовать напрямую записать `locale=ru-RU` в колонку, минуя приложение.
- BLE Weave GATT имеет отдельную характеристику **`language`** (`aghn.java`). Записать её напрямую.
- Обе — прямые команды устройству. Ограничение то же: примет ли прошивка значение, которого нет в её собственном списке. Но проверить дёшево и это обходит весь клиент целиком.

## 5. Инфраструктурный вектор (разблокирует §2.2/§3 «по-взрослому»)

### 5.1. LSPosed signature spoofing
Обозначен как следующий шаг в прошлой сессии. Ставится через Magisk + модуль подмены подписи. Даёт: патчить APK Google Home **и сохранить доверие GMS** (то, обо что разбился подход №3), а также логировать/патчить саму GMS. Существенный по объёму сетап, но открывает чистый путь ко всем клиентским векторам без Frida-хрупкости и без потери GMS-функциональности. Разумно делать, только если §2 (дешёвые) не сработали, а Ветка = A (т.е. известно, что клиент — реальный гейт).

## 6. Рекомендованная последовательность

1. **§1 — `GET /setup/supported_locales` + полный `eureka_info` с колонки.** Один запрос решает, ветка A или B. **Всё остальное зависит от результата.**
2. Параллельно (не требует устройства, обратимо): **§3.1 регион аккаунта = Россия**, **§3.3 проверить iOS-приложение**, **§3.2 второй язык Assistant**.
3. **RE-довесок** (можно на текущей декомпиляции `jadx-out`, устройство не нужно): значение `lM().u` для L09G (нужен ли экран выбора); точный файл/ключ SharedPrefs с кэшем флага (для §2.2); GServices-ключ флагов (для §2.3).
4. **Если Ветка A:** §2.1 (локаль телефона) → если мало, §2.2 (патч SharedPrefs) → §2.3 (GServices). Дёшево и без слома GMS.
5. **Если Ветка B:** §4.3 (прямая запись locale в устройство — дёшево проверить) → §4.1 (подмена ответа `supported_locales` в MITM) → §4.2 (firmware/UART, самый тяжёлый).
6. §5 (LSPosed) — только если клиентский путь подтверждён как гейт, но упирается в GMS-доверие.

- `lM().u` для L09G: откуда берётся `ahtq.u` — из `akdv`-enum модели или из ответа устройства? Файл `ahtq.java` + `akdv.java` (`aa`/`ae`-поля).

## 8. Историческое наблюдение: метод ЧАСТИЧНО работал (сдвигает приоритеты) ★★

Пользователь >6 лет назад проходил MITM-метод через эмулятор Memu (Android 5.1.1) — полная инструкция сохранена в `historical-mitm-instruction-memu-2019.md`. **Результат: колонка отвечала на русском самый первый раз, затем снова переходила на английский.** Это максимум, который метод давал.

### Что это доказывает (важнее самого метода)

1. **Прошивка + бэкенд УМЕЮТ русский для L09G.** Раз колонка *произнесла* русский хотя бы раз — русский TTS/распознавание для этой модели существует. Значит **мы почти наверняка НЕ в безнадёжной Ветке B** (§1). Гейт — не способность устройства, а **закрепление**.
2. **Проблема — авторитетность/персистентность слоя, а не установка значения.** «Русский один раз → откат в английский» — это учебниковая **сигнатура рассинхронизации трёх слоёв локали** (MITM-doc §11, session-report §0):
   - **Слой 1 — device-side локаль** (то, что байтовая замена `en-US→ru-RU` проставляет в setup-трафике / `ahtq.bn`-матч / `set_eureka_info`). Именно он дал «первый ответ на русском».
   - **Слой 2 — Assistant Settings profile аккаунта.** Официальный `embedded_assistant.proto` прямо говорит: **язык, выбранный в Settings, перекрывает `language_code`, присланный клиентом в рантайме.** В инструкции English оставлен ВТОРЫМ языком → бэкенд легально откатывается на него.
   - **Слой 3 — locale voiceprint-модели Voice Match.** Голос энролен под en → confidence для русского низкий → откат.
   - После первого ответа бэкенд ре-синхронизирует авторитетные слои 2/3 поверх слоя 1 → возврат в английский.

### Как это переставляет приоритеты

- **Побеждает не тот, кто установит `ru-RU`, а тот, кто сделает АВТОРИТЕТНЫЙ слой моноязычно русским.** То есть вектора §3 (серверные/аккаунтные) поднимаются с «параллельных» до **первоочередных**, а не вспомогательных.
- Конкретно то, чего исторический метод НЕ доделал:
  - **Убрать English из языков Assistant полностью** (оставить только Русский — нюанс (c) инструкции на это и намекал, но с двумя языками слой 2 оставался двуязычным и откатывался). Проверить, даёт ли аккаунт сейчас выставить *единственным* языком ассистента русский при том, что колонка привязана.
  - **Переэнролить Voice Match под русский (слой 3).** Ключ: Android-приложение Google Home **не показывает** Voice Match для колонок — только **iOS-приложение** (MITM-doc §11). → вектор §3.3 (iOS) становится не «дёшево если есть железо», а **вероятно необходимым звеном для закрепления**.
- **grpc-dump неслучаен.** Установка языка идёт по gRPC (слой 2), и старый mitmproxy 2.0.2 его ломал — метод переключался на grpc-dump, чтобы gRPC-провижининг прошёл. В наших терминах: закрепляющий запрос — **gRPC к Assistant/Foyer**, а не HTTP setup-канал. Это подтверждает вывод session-report §2: «нужный устанавливающий-локаль запрос — вероятно protobuf enum в gRPC, которого побайтовая замена не видит». **Приоритет для MITM-ветки: не байтовая замена, а gRPC-aware перехват+модификация Foyer/Assistant-канала** (grpc-tools/grpc-fixture, а не mitmproxy `--replace`).

### Практический вывод для последовательности §6

Вставить перед тяжёлыми векторами: **сначала атаковать слой закрепления (2+3), а не слой установки (1).**
1. Языки Assistant аккаунта → **только Русский** (без English вторым). Проверить, держится ли теперь.
2. Voice Match переэнрол под русский через **iOS-приложение** (§3.3).
3. Если для показа/сохранения нужен gRPC-перехват — брать **grpc-fixture/grpc-dump**, целясь в Foyer/Assistant-канал, а не mitmproxy byte-replace.
4. Только если это не держит — идти в клиентские патчи §2 и firmware §4.

> Важный нюанс воспроизводимости: исторический метод работал на **Android 5.1.1 (user-CA доверяется штатно)** и на **древних билдах** Google/Home. Повторять его «как есть» имеет смысл именно в **эмуляторе Android ≤6 со старыми APK** — это на порядок проще, чем весь Magisk/system-CA-ад прошлой сессии, и ближе к условиям, в которых метод реально давал (частичный) результат.

## 10. РАЗГАДКА: точный эндпоинт локали (файл ru.img получен и вскрыт) ★★★

`ru.img` найден и перенесён в проект (`/Users/ieffai/code/home-ru/ru.img`). Это не образ, а mitmproxy-аддон в 9 строк. Полный смысл:

```python
def request(flow):
    if flow.request.host == "clients3.google.com":
        if "set_assistant_language" in flow.request.data.path:
            flow.request.data.content = flow.request.data.content.replace(b'en-US', b'ru-RU')
```

То есть подмена локали происходит **строго в одном запросе**, и мы теперь знаем в каком точно.

### Полный адрес и структура (подтверждено декомпиляцией, актуально и в текущем билде)

- **URL:** `https://clients3.google.com/cast/orchestration/set_assistant_language?rt=b`
  - `clients3.google.com` — Phenotype-флаг `45355692` (`bnbk.java:37`).
  - `/cast/orchestration` — `acch.dj()` (`acch.java:2290`).
  - `/set_assistant_language?rt=b` — класс `tey.java` = **`SetSurfaceAssistantLanguageRequest extends vpg`**. Парный `tew.java` = `GetSurfaceAssistantLanguageRequest` (`/get_assistant_language?rt=b`).
- **Тело — protobuf `aqza`** (`aqza.java`): строковые поля `c`, `e`, `f` + submessage `d` (`aqif`, enum). Локаль лежит одним из строковых полей как literal `en-US`.
- **Байтовая замена работает, потому что** `en-US`↔`ru-RU` — ровно 5 байт: varint-length-prefix protobuf-строки не сдвигается, сообщение остаётся валидным (тот же принцип, что в MITM-doc §4б).
- **Строит запрос** `aevo.i(String str, String str2, int i, Consumer)` (`aevo.java:433-475`): `aqza.e=str`, `aqza.c=str2` (одно из них — код языка), `aqif.c=i-1` (enum surface-типа), `aqza.f=str3` (`((aiiw)this.a).a` — id поверхности/устройства). Это **per-surface** установка языка ассистента → пишет авторитетный серверный слой 2 именно для этой колонки.

### Почему это закрывает 4 сессии гадания

- Это **НЕ** `deviceuserlinksbatch` (`teq.java`) — тот, что прошлая сессия ждала и «ни разу не поймала». Это **отдельный эндпоинт `set_assistant_language`** на том же хосте.
- Это **НЕ** Foyer gRPC (метод 2022 его игнорит) и **НЕ** локальный API колонки.
- Наш `relocalize.py` бил слепой заменой `en-US→ru-RU` по всему `clients3.google.com` — то есть **теоретически поймал бы и этот запрос**. Раз в логах прошлой сессии по clients3 сработали только косметические response-замены (`GetFeed`, `eureka_info`), а `set_assistant_language` — нет, вывод: **в модерн-флоу (Android 10 + свежий Home) этот запрос при онбординге просто не выстрелил** (либо ушёл иным транспортом, либо шаг подтверждения языка не был достигнут). Ровно поэтому исторический метод настаивает на **старых APK (Home 2.25.1.5)**: там механизм — этот HTTP-protobuf на clients3, и он ловится.

### Что делать (максимально конкретно)

1. **Немедленный дешёвый апгрейд `relocalize.py`:** сузить до правила ru.img — `host==clients3.google.com and "set_assistant_language" in path → request body en-US→ru-RU`, плюс verbose-лог **факта попадания** в этот эндпоинт (видели ли мы его вообще). Это отвечает на главный вопрос «выстреливает ли `set_assistant_language`» в любом сетапе за один прогон.
2. **Основной путь — воспроизвести 2022 в эмуляторе Android 5.1 со старыми APK** (Home 2.25.1.5, Google 10.33.5.21), запустить `ru.img` как есть с ignore-list, на шаге языка выбрать English (US). Всё готово: файл, эндпоинт, версии, ignore-list — известны.
3. **Диагностика closure-петли:** после успешной подмены снять `GET /get_assistant_language?rt=b` (`tew`) — убедиться, что сервер вернул `ru-RU` обратно (закрепилось на слое 2), а не откатил. Если `get_` показывает ru, а колонка всё равно ушла в английский — остаётся только слой 3 (Voice Match, §8) → iOS-retrain.
4. **Проверить, зовёт ли `set_assistant_language` современный билд при онбординге L09G** (греп живого трафика или трассировка `aevo.i` через Frida) — если да, модерн-путь тоже жизнеспособен без эмулятора; если нет — эмулятор обязателен.

> Итог переоценки: главный неизвестный «где в трафике локаль» — **закрыт**. Осталось два эмпирических вопроса: (а) выстреливает ли `set_assistant_language` в доступном нам флоу, (б) закрепляется ли результат или откатывается слоем Voice Match. Оба проверяются за один прогон 2022-схемы.

## 11. Эмпирический прогон 2026-07-24 (модерн-телефон) — РЕЗУЛЬТАТ ОТРИЦАТЕЛЬНЫЙ, но решающий ★★★

- Путь «прицельный MITM на современном телефоне» **закрыт** для этого билда. Подтверждается вывод §9/§10: **нужен эмулятор Android 5.1 + старые APK (Home 2.25.1.5, Google 10.33.5.21)**, где `set_assistant_language` — живой механизм, ловится и переворачивается `ru.img`.

- Следующий заход делать **в эмуляторе**, не на телефоне.

## 13. Проверка путей в конце сессии 2026-07-24 — что отпало, что осталось

После перелома (§12) пробовали два дешёвых финиша прямо на телефоне. Оба упёрлись в конкретику — важно для следующего захода.

### Отпало
- **§4.3 прямая запись `set_eureka_info locale=ru` в колонку → HTTP 401.** Привязанное устройство требует `cast-local-authorization-token` (LAT) на запись (чтение — без токена). Локаль осталась `en-US`, ничего не сломано, бэкап eureka снят.
- **LAT на телефоне не закэширован.** `/data/data/com.google.android.gms/databases/cast.db` (таблица `DeviceInfo`) содержит наше устройство (`model=Mi Smart Speaker`, device_id `2d8da8b907d76ce0aaad113e03292e30`, cloud_id `643A1B116E60FA4A4F298A277DC5C250`), но из токенов там только `relay_access_token` (облачный relay, protobuf-блоб) — **не** setup-LAT. На телефоне нет `sqlite3`.
- **§2.2 «простой патч prefs» — невозможен.** Списки локалей (флаги `45356207/08/708`) НЕ лежат в `shared_prefs` приложения (греп по CSV и по ID флагов пуст). Phenotype в этом билде хранит значения в GMS/бинарно, не в открытых prefs. Правка файла отпадает.

### Осталось два реальных финишных пути (оба — самостоятельные под-задачи, не «на минуту»)

**Путь A — LAT через аккаунт → прямая запись (самый детерминированный).**
Устройство доказано принимает `ru`; не хватает только токена. Через glocaltokens-подход: `master_token` Google-аккаунта → обмен на `localAuthToken` устройства (cloud_id `643A1B…`) → `POST /setup/set_eureka_info {"locale":"ru"}` с заголовком `cast-local-authorization-token`. Плюс: детерминированно, без re-onboard, без Frida, повторяемо. Минус: трогает master-token аккаунта (чувствительно; держать только в памяти, не логировать). Инструмент: python-библиотека `glocaltokens` (та же, что в Home Assistant Google Home integration). Master-token добывается либо через gpsoauth (нужен app-password аккаунта), либо извлечением из GMS на рут-телефоне.

**Путь B — Frida-хук списка языков (без кредов аккаунта).**
Захукать актуальный диспетчер списка локалей (в старой декомпиляции `koo.A`, в билде из прошлой сессии `knf.v` — в установленном `4.20.63.1` имя надо переуточнить: `adb pull` актуального `base.apk` → декомпиляция → найти метод по флагам `45356207/08/708`), дописать `ru-RU` в возвращаемый CSV. Затем **re-onboard колонки с активным хуком** (прокси НЕ нужен — онбординг без нашего прокси прошёл нормально), на экране языка выбрать русский → `av.h="ru-RU"` → `ahtq.e("ru-RU","ru")` мапит на устройство `ru` → провижининг русский. Плюс: без аккаунтных кредов, всё локально. Минус: хрупкость Frida (терялся при рестарте процесса — §5), обфусцированное имя привязано к билду, нужен re-onboard.

### Рекомендация
**Путь A** как основной: раз устройство пров́ерено принимает `ru`, чистая запись `locale=ru` с валидным LAT — ближе всего к гарантированному результату за один шаг. Если после записи язык откатится («русский один раз») — добить слой закрепления §8 (единственный язык Assistant = русский, Voice Match retrain через iOS). **Путь B** — если не хотим трогать master-token.
