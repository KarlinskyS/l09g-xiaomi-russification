# Отчёт по сессии 2026-07-24: попытка русификации Xiaomi Mi Smart Speaker L09G через Google Home

## Итоговый статус: НЕ ДОСТИГНУТО

Русский язык не появился ни на экране выбора языка в приложении Google Home, ни (соответственно) на самой колонке. Опробовано четыре независимых подхода, три исчерпаны/провалены, четвёртый (наиболее многообещающий) прерван на середине из-за потери Frida-сессии — технически жизнеспособен, но не доведён до результата.

Сессия остановлена по прямому запросу пользователя ("пора делать точку остановки"), не из-за отсутствия дальнейших вариантов.

---

## 0. Контекст и цель

Задача: заставить Xiaomi Mi Smart Speaker L09G (кодовое имя `dipper`, привязана к Google Assistant) работать на русском языке, хотя UI Google Home официально не предлагает русский для этой модели/аккаунта — виден только client-side allowlist языков без `ru-RU`.

Заранее существовавшие материалы в проекте (до этой сессии):
- `google-assistant-mitm-russification-l09g.md` — реконструкция найденной где-то методики (MITM-прокси + подмена `en-US`→`ru-RU` в трафике).
- `google-home-onboarding-re-report.md`, `l09g-device-teardown-research.md` — сопутствующие исследования.
- `google-home-russian/` — готовый staged-пайплайн (`bootstrap.sh` + `stages/00..70`) под этот MITM-подход: preflight, python-env, mitmproxy, certificates, proxy-runtime, device-instructions, verification, export.
- `apktool-out/`, `jadx-out/`, `splits/` — уже декомпилированный APK Google Home (версия на момент начала сессии) и сохранённые оригинальные APK-сплиты (`base.apk`, `config.ru.apk`).

Ключевая цитата из `google-assistant-mitm-russification-l09g.md` (написана ДО этой сессии, целиком подтвердилась практикой):
> Язык в экосистеме Google Assistant хранится минимум в трёх независимых слоях — (1) язык системы Android на телефоне, (2) язык в Assistant Settings профиля аккаунта, (3) locale, привязанная к voiceprint-модели Voice Match. MITM-подмена на этапе setup с высокой вероятностью обновляет только один слой... Не найдено ни одного отчёта [об успехе].

## 2. Подход №1: MITM-прокси (mitmproxy) + доверие CA на телефоне

### Что делали и как запускали

1. **Установка CA-сертификата как user store**: `adb push` сертификата в `/data/misc/user/0/cacerts-added/<hash>.0` через `su -c`.
2. **Обнаружился первый барьер — SELinux**: даже под root (`su`, домен `u:r:magisk:s0`/`magisk_client`) прямая запись в некоторые системные директории (`/data/misc/user/0/cacerts-added/`, позже директория Magisk-модуля) периодически давала `Permission denied` — непоследовательно: то `touch` проходил, то нет; `cp`/`chmod` иногда падали, иногда нет. Причина не до конца выяснена (SELinux не в permissive, официальный `setenforce 0` пользователь сознательно не разрешал использовать как первый вариант).
3. Пользователь физически установил CA как **пользовательский** сертификат через **Настройки → Безопасность → Установить сертификат** (штатный Android-механизм) — сертификат появился в Trusted Credentials → User.
4. **Тест показал: user-store сертификата недостаточно.** В логе mitmproxy: `Client TLS handshake failed. The client does not trust the proxy's certificate for googlehomefoyer-pa.googleapis.com` — при этом обычный HTTPS к сторонним (не Google) доменам через тот же прокси проходил нормально. Начиная с Android 7+, приложения с `targetSdk>=24` по умолчанию не доверяют user-added CA, только system store.
5. **Подъём CA в system store потребовал Magisk-модуля.** Первая попытка — установленный модуль оказался `AlwaysTrustUserCerts` (NVISO, v1.3) с рабочим `post-fs-data.sh`, который **сам собирает** сертификаты из `cacerts-added` при каждой загрузке — но пользователь позже поставил "исправленную" версию (v0.4, NVISO + NowSecure), у которой `common/service.sh` оказался **пустым шаблоном** — сбора сертификатов не происходит вообще.
6. Пришлось **вручную** копировать сертификат прямо в директорию модуля (`/data/adb/modules/trustusercerts/system/etc/security/cacerts/`), которая монтируется Magisk'ом поверх `/system/etc/security/cacerts` при загрузке. Здесь встретили точную причину постоянных SELinux-отказов: директория модуля промаркирована меткой `u:object_r:system_file:s0` (чтобы корректно "притворяться" частью `/system` при monut), а домен `magisk` **не имеет права записи** в объекты с этой меткой.
   - **Обходной путь (сработал)**: `chcon u:object_r:adb_data_file:s0 <dir>` → скопировать файл → `chcon u:object_r:system_file:s0` обратно на файл и директорию → **перезагрузка** (чтобы Magisk на следующей загрузке заново создал bind-mount с правильным содержимым).
   - После перезагрузки подтверждено через `mount | grep <hash>`: `/dev/block/sda21 on /system/etc/security/cacerts/<hash>.0 type ext4 (ro,...)` — сертификат реально смонтирован в system store.
7. **`adb remount` / прямая перезапись `/system` НЕ делали** — из-за заблокированного bootloader + green AVB это было признано слишком рискованным (реальная опасность bootloop), явно предложено и отклонено пользователем в пользу chcon-обхода.
8. **Обнаружился второй барьер — локальный API колонки.** Frida-скрипт `native-connect-hook.js` (см. подход №2 ниже) заворачивает **весь** TCP-трафик приложения через прокси, включая обращения к самой колонке по локальной сети (`https://192.168.1.x:8443/setup/eureka_info`, `/setup/assistant/check_ready_...` и т.п. — локальный HTTPS API колонки с самоподписанным сертификатом). mitmproxy пытался домитмить и его, но падал: `Server TLS handshake failed. Certificate verify failed: unable to get local issuer certificate` — из-за чего "Подключение к устройству" зависало намертво.
   - **Фикс**: добавить `--set ssl_insecure=true` в команду запуска `mitmdump` (отключает проверку **upstream**-сертификата со стороны mitmproxy; правка внесена постоянно в `stages/40-proxy-runtime/run.sh`).
9. **Обнаружился третий барьер — leaf-сертификат слишком долгоживущий.** После фикса ssl_insecure появилась новая, куда более коварная ошибка в logcat приложения:
   ```
   net::ERR_CERT_VALIDITY_TOO_LONG, ErrorCode=11, InternalErrorCode=-213
   at org.chromium.net.impl.CronetBidirectionalStream.onError (com.google.android.gms.dynamite_cronetdynamite)
   ```
   Это **не pinning и не user/system-store** — отдельная политика сетевого стека Cronet (используется частью Google-компонентов, в т.ч. `cryptauthenrollment.googleapis.com`), которая отклоняет сертификаты со слишком долгим сроком действия, **даже если CA доверенный**. Причина найдена в исходнике mitmproxy:
   ```python
   # mitmproxy/certs.py, комментарий в коде: "Default expiry must not be too long: https://github.com/mitmproxy/mitmproxy/issues/815"
   CERT_EXPIRY = datetime.timedelta(days=365)  # → фактическая валидность leaf-сертификата 367 дней
   ```
   367 дней технически меньше публичного лимита CA/B Forum (398 дней), но Cronet-валидация для чувствительных Google-эндпоинтов, судя по всему, ещё строже.
   - **Фикс (прямой патч установленного пакета в venv)**: `runtime/venv/lib/python3.14/site-packages/mitmproxy/certs.py` строка 34 — `CERT_EXPIRY` изменено с `days=365` на `days=30`. После перезапуска `mitmdump` TLS-рукопожатия с ранее падавшими доменами (`www.googleapis.com`, `play.googleapis.com` и т.д.) стали проходить чисто.

### Что получили в итоге

После всех трёх фиксов (system-store CA + ssl_insecure + короткий cert expiry) TLS-перехват заработал технически полностью — **но** это не решило исходную задачу:

- Аддон `stages/40-proxy-runtime/addons/relocalize.py` делает побайтовую замену `en-US`↔`ru-RU` (и вариаций регистра/разделителя) в HTTP-трафике к allowlist-доменам (`accountlinking-pa.googleapis.com`, `clients3.google.com`, `googlehomefoyer-pa.googleapis.com`, `oauthaccountmanager.googleapis.com`) + локальный порт колонки 8443.
- За **два полных цикла** (включая полный factory reset колонки + повторную привязку с нуля между ними) единственный **подтверждённый по документу проекта** эндпоинт привязки локали — `POST clients3.google.com/cast/orchestration/deviceuserlinksbatch?rt=b` — **ни разу не был вызван** (кроме одного случая рано утром, вероятно из более раннего/другого теста, ещё до начала этой сессии диагностики).
- Реально сработавшие замены за оба цикла — чисто косметические, **response**-направленные (не отправляются на сервер, только видоизменяют то, что придёт в приложение): `GetFeed` (6 замен), `eureka_info` (1 замена).
- **Вывод**: сервер Google по-прежнему считает устройство/аккаунт англоязычным — колонка привязывается и работает, но говорит и понимает только по-английски. Это ровно тот сценарий рассинхронизации трёх слоёв локали, который заранее предсказывал `google-assistant-mitm-russification-l09g.md`.

### Новые знания

- MITM-перехват технически полностью настроен и работоспособен на этом устройстве (все три барьера преодолены), но сам факт перехвата НЕ гарантирует, что нужный "устанавливающий локаль" запрос вообще пройдёт через сеть в узнаваемом виде — либо он использует другой энкодинг (protobuf enum/число вместо строки `"en-US"`), либо этот механизм в текущей версии приложения работает иначе, чем предполагал исходный research-документ.
- `googlehomefoyer-pa.googleapis.com` — активный gRPC-канал (десятки вызовов за сессию привязки), но конкретно строковый паттерн локали в нём почти никогда не встречается.

## 3. Подход №2: Frida certificate unpinning

Параллельно с подходом №1 понадобился обход certificate pinning в самом приложении/Google Play Services (иначе TLS рвался на `googlehomefoyer-pa.googleapis.com` и подобных даже с доверенным system-store CA).

### Что делали и как запускали

1. Установлен `frida-tools` в venv проекта: `runtime/venv/bin/pip install frida-tools` → подтянул **frida 17.16.4** (клиент).
2. Скачан соответствующий `frida-server-17.16.4-android-arm64` с GitHub releases, залит на телефон в `/data/local/tmp/`, запущен через `su`.
3. **Критический барьер**: с активным `frida-server` 17.16.4 **любое** новое приложение на телефоне (не только Google Home — воспроизведено и на Chrome) валилось с `Fatal signal 11 (SIGSEGV), code 2 (SEGV_ACCERR)` **в момент zygote-форка**, ещё до старта кода самого приложения. Флаг `--policy-softener=system` (специально существующий у frida-server для конфликтов с Magisk на MIUI) **не помог** — краш идентичный, тот же fault address.
   - **Диагностика подтвердила**: это не anti-Frida детект в приложении (краш происходит до старта прикладного кода), а несовместимость конкретно этой версии frida-server с zygote данной прошивки/ядра MIUI.
4. **Фикс**: отдельный venv (`runtime/frida-old-venv/`) с **frida 16.5.9** + соответствующий `frida-server-16.5.9-android-arm64`. С этой версией Chrome и Google Home запускаются нормально под активным frida-server.
5. Склонирован референсный тулинг: `git clone https://github.com/httptoolkit/frida-interception-and-unpinning.git` → `runtime/frida-unpinning/`.
6. `config.js` заполнен: `CERT_PEM` (наш mitmproxy CA), `PROXY_HOST=192.168.1.187`, `PROXY_PORT=8888`.
7. Стандартный запуск (полный набор скриптов из README проекта):
   ```bash
   frida-old-venv/bin/frida -U \
       -l config.js \
       -l native-connect-hook.js \
       -l native-tls-hook.js \
       -l android/android-proxy-override.js \
       -l android/android-system-certificate-injection.js \
       -l android/android-certificate-unpinning.js \
       -l android/android-certificate-unpinning-fallback.js \
       -l android/android-disable-root-detection.js \
       -f com.google.android.apps.chromecast.app
   ```
   (позже переключились на `-p <pid>` — attach к уже запущенному процессу, а не `-f` spawn, чтобы не сбрасывать прогресс мастера настройки).
8. **Важный найденный нюанс**: если приложение уже успело установить какое-то TLS-соединение/канал ДО присоединения Frida (`-p` к уже работающему процессу), у этого конкретного соединения перехват может не сработать (похоже на кеширование состояния в конкретном канале) — надёжнее спаунить (`-f`) заново, если это не критично для прогресса UI.

### Что получили

- Полностью рабочий unpinning для большинства Google-доменов (после совместных фиксов подхода №1 — ssl_insecure и короткий cert expiry).
- НЕ решило исходную задачу (см. раздел 2 — проблема не в pinning, а в отсутствии нужного сетевого запроса вообще).

### Новые знания

- **frida-server 17.x несовместим с zygote этой конкретной прошивки MIUI/ядра** — крашит любое приложение. **frida-server 16.5.9 совместим.** Это стоит проверять в первую очередь на будущих MIUI-устройствах перед долгой отладкой unpinning-скриптов.
- `--policy-softener=system` не помогает при данном типе краша (это не SELinux-конфликт, а более низкоуровневая несовместимость инжектора).
- Frida `native-connect-hook.js` перехватывает вообще все TCP-соединения приложения, включая локальные (не только к Google) — нужно об этом помнить, если приложение параллельно общается с локальными устройствами (в нашем случае — с самой колонкой по локальному HTTPS API).

## 4. Подход №3: Патчинг APK (client-side allowlist языков) — ПРОВАЛЕН, откачен

После того как стало ясно, что MITM не ловит нужный запрос, сменили стратегию: убрать ограничение языка прямо в приложении, чтобы русский был доступен в UI нативно, без сетевых фокусов.

### Что делали и как запускали

1. Задача поиска, где именно в APK формируется список языков, делегирована агенту (subagent Explore) на декомпилированный код (`apktool-out/` — smali, `jadx-out/` — Java-псевдокод, версия APK на момент НАЧАЛА сессии).
2. Агент нашёл: список — это **захардкоженный дефолт Phenotype-флага** (client-side feature flag GMS), а не resource-array. Класс `Lbnrv;` (smali `apktool-out/smali_classes3/bnrv.smali`), три CSV-строки локалей под флагами `"45356207"`, `"45356208"` (строка 379 — общий список без ru-RU) и `"45356708"` (строка 431 — расширенный список, тоже без ru-RU). Диспетчер — `defpackage.koo.A(int i)` (`apktool-out/smali/koo.smali`), вызывается из `defpackage.wbr` (фрагмент экрана выбора языка, layout `language_selection_new`).
3. **Попытка №1 — официальный механизм переопределения флага без патчинга APK**: у GMS есть `com.google.android.gms/.phenotype.service.FlagOverrideReceiver`, реагирующий на broadcast `com.google.android.gms.phenotype.FLAG_OVERRIDE` — штатный (используемый инженерами Google для отладки) способ локально переопределить Phenotype-флаг, **имеющий приоритет над серверной синхронизацией**.
   - Декомпилирован сам `com.google.android.gms` (base.apk, ~199 МБ, 15 dex-файлов) — `apktool d -r`.
   - `FlagOverrideReceiver` в манифесте требует `android:permission="com.google.android.gms.permission.PHENOTYPE_OVERRIDE_FLAGS"`.
   - Реальная логика делегирована в динамически подгружаемый **Chimera-модуль** Google (архитектура модульной загрузки GMS) — статически не резолвится, точный формат broadcast-extras узнать через декомпиляцию не удалось.
   - Попытка broadcast вручную (`adb shell su -c 'am broadcast -a com.google.android.gms.phenotype.FLAG_OVERRIDE --es package ... --es flag 45356708 --es flagType string --es value "...,ru-RU"' com.google.android.gms`) — broadcast ушёл (`result=0`), но последующий `content query` к Phenotype ContentProvider вернул `SecurityException: Caller is not authorized to access Uri` — **GMS проверяет вызывающего по имени пакета/подписи отдельно от Linux UID, root не помогает обойти эту проверку**. Путь закрыт.
4. **Попытка №2 — прямой патч + пересборка APK**:
   - В `bnrv.smali` добавлено `ru-RU` в обе CSV-строки (379 и 431).
   - Пересборка: `apktool b apktool-out -o chromecast-patched.apk`.
   - Установка Android SDK build-tools (`brew install --cask android-commandlinetools`, `sdkmanager "build-tools;34.0.0"`) для `apksigner`/`zipalign` (обычный `jarsigner` дал только V1/JAR-подпись — недостаточно для `targetSdk>=28`, установка падала с `INSTALL_FAILED_VERIFICATION_FAILURE` до этого шага уже по другой причине, см. ниже).
   - Сгенерирован self-signed debug keystore (`keytool -genkeypair`), APK выровнен (`zipalign`) и подписан (`apksigner sign`, успешно верифицирован V3-схемой).
   - Установка `adb install-multiple` **base + config.ru** (оригинальный сплит, тоже переподписанный тем же ключом, т.к. подписи должны совпадать в одной сессии установки) — упёрлась в `INSTALL_FAILED_VERIFICATION_FAILURE`: Play Protect (**Finsky**) блокировал установку из-за **отсутствующих сплитов** (`missing splits: [base__abi, base__density]` — в сохранённом `splits/` были только `base.apk` и `config.ru.apk`, без abi/density сплитов).
   - **Обход**: `adb shell settings put global verifier_verify_adb_installs 0` + `package_verifier_enable 0` — установка прошла успешно.
5. **Фатальная находка**: с переподписанным (не Google-ключом) APK Google Play Services **полностью отказывает приложению в доступе к своим API**:
   ```
   SecurityException: PackageVerificationRslt: not allowed: pkg=com.google.android.apps.chromecast.app, sha256=[...]
   SecurityException: GoogleCertificatesRslt: not allowed: pkg=..., sha256=[...]
   ```
   Это отдельная, **встроенная в саму GMS** проверка подписи вызывающего приложения (`GoogleApiManager`/`Auth`) — не имеет отношения к обычной Android-проверке сигнатур при установке. Результат: `GetLinkUsers request failed (403)`, `homeGraph is null`, невозможность получить аккаунты, зависание на "аккаунт уже есть на устройстве". **Приложение становится полностью нефункциональным для любых Google-account-зависимых операций** (что покрывает весь use case привязки колонки).

### Откат

- Приложение удалено (`adb uninstall`) и переустановлено сначала вручную из сохранённых `splits/base.apk` + `splits/config.ru.apk` (тоже потребовало `verifier_verify_adb_installs=0` из-за неполного набора сплитов), затем — по требованию пользователя добиться полной функциональности — **переустановлено окончательно через сам Play Store** (`market://details?id=...`, пользователь нажал "Установить"), что восстановило полный набор сплитов (`base`, `split_config.arm64_v8a`, `split_config.ru`, `split_config.xxhdpi`) и настоящую подпись Google.
- Настройки `verifier_verify_adb_installs`/`package_verifier_enable` возвращены в `1` (штатное состояние) в конце сессии.

### Новые знания

- **Патчинг + переподпись Google-приложения принципиально ломает его интеграцию с Google Play Services** — это не обходится без настоящего приватного ключа Google или без более глубокого вмешательства в саму GMS (например, signature spoofing framework вроде LSPosed/Xposed-модуля — НЕ пробовали в этой сессии, требует установки LSPosed через Magisk + отдельного модуля подмены подписи, это отдельная существенная по объёму задача).
- Официальный Phenotype `FLAG_OVERRIDE` broadcast механизм существует, но практически недоступен извне (GMS проверяет вызывающий пакет отдельно от root/UID).
- Play Store переустановка — самый надёжный способ вернуть полный/корректный набор сплитов и подпись после экспериментов.

## 5. Подход №4: Frida runtime-хук на языковой список (оригинальное подписанное приложение) — ПРЕРВАН, не завершён

Идея: не трогать подпись APK вообще — оставить оригинальное Google-подписанное приложение (GMS ему доверяет), но через Frida **на лету** подменить возвращаемое значение диспетчер-метода (`koo.A(int)` / актуальное имя может отличаться по сборкам, см. ниже), дописав `ru-RU` в CSV-список. Если сработает — сама igra отправит `ru-RU` как естественный выбор через штатный, доверенный код, без необходимости ловить что-либо в сети.

### Что делали и как запускали

1. `runtime/frida/locale-hook.js` — Java-хук через `Java.perform` + `Java.enumerateClassLoaders` (нужно перебирать classloader'ы, а не брать дефолтный — целевой класс приложения не загружен в classloader по умолчанию на момент старта скрипта).
2. **Проблема №1**: изначальный хук на `koo.A` (имя класса/метода взято из СТАРОЙ декомпиляции `apktool-out/`, версия APK с начала сессии) — `TypeError: cannot read property 'overload' of undefined`. Причина: неправильный classloader (нашёл общий default classloader без реальных классов приложения).
3. **Проблема №2** (после фикса classloader-перебора через фильтр по `loader.toString().indexOf('chromecast')`): класс `koo` **найден в ДВУХ РАЗНЫХ classloader'ах** — один принадлежит `chromecast.app`, другой — динамически подгруженному модулю `com.google.android.gms` внутри того же процесса (Chimera-модули GMS используют отдельные classloader'ы поверх собственных APK-файлов GMS, но живут в том же процессе-хосте). Это **разные, никак не связанные классы**, которым обфускатор (R8/Proguard) случайно присвоил одинаковое короткое имя `koo` в двух независимых сборках/модулях.
4. Даже после фильтрации по `chromecast` в имени classloader'а, реальный класс `koo` в текущей (**заново скачанной через Play Store**, другой версионный билд — `versionCode=30567414`, `versionName=4.20.63.1`, чем то, что было декомпилировано в начале сессии) сборке оказался **вообще не тем классом** — методы у него только `a(MessageDigest)` и `toString()` (проверено через `koo.class.getDeclaredMethods()` прямо в живом процессе).
5. **Пришлось декомпилировать ЗАНОВО именно текущую установленную версию** APK (`adb pull` актуального `base.apk` с телефона → `apktool d -r`), чтобы найти актуальные обфусцированные имена. Найдено:
   - Класс с флагами локали теперь называется `Lbnjh;` (не `Lbnrv;`), но структура идентична: те же ID флагов (`45356207`, `45356208`, `45356708`), те же CSV-списки (без ru-RU), методы-геттеры `J()`/`K()`/`L()` через интерфейс `Lbnjg;`.
   - Диспетчер-метод — теперь `knf.v(I)Ljava/lang/String;` (не `koo.A(I)Ljava/lang/String;`). **Обфусцированные короткие имена классов/методов меняются от сборки к сборке** — жёстко закодированные имена из одной декомпиляции ненадёжны для другой версии APK.
6. Хук переписан на `knf.v`, переприсоединён к уже запущенному процессу (`-p <pid>`, без потери прогресса мастера) — **успешно установлен**: в выводе Frida `[locale-hook] knf.v hook installed via chromecast classloader`.
7. **Пользователь проверил экран выбора языка — русский не появился.**
8. **Диагностика причины провала (в конце сессии)**: PID процесса приложения на момент проверки (`4517`) оказался **другим**, чем PID, к которому был присоединён хук (`3286`) — то есть между установкой хука и проверкой пользователем **приложение перезапустилось** (вероятно, ушло в фон/было убито системой или пользователем случайно), и Frida CLI сессия к тому моменту уже сама отсоединилась (в выводе фоновых задач несколько раз приходили `status: failed` уведомления о завершении frida-процесса — истолкованы как безобидное отсоединение контроллера, что в целом верно для Frida, НО в данном случае реальный процесс-мишень тоже сменился, так что хук физически отсутствовал в новом процессе).

### Текущее состояние на момент остановки

- Хук **технически рабочий** (метод найден правильно, инжектируется без ошибок, логика подмены строки проверена в коде), но **не был активен** в процессе, который пользователь фактически тестировал.
- `locale-hook.js` в текущем виде **захардкожен под конкретный build** (`knf.v`) — если Play Store снова обновит приложение, имена почти наверняка опять изменятся, и потребуется повторный цикл "pull APK → decompile → найти новые имена".

### Что нужно сделать для завершения этого подхода (следующие шаги)

1. Убедиться, что `frida-server` (версия **16.5.9**, НЕ 17.x — см. раздел 3) запущен на телефоне: `adb shell su -c '/data/local/tmp/frida-server-16 &'`.
2. Проверить, что установленная версия приложения всё ещё та же (`adb shell dumpsys package com.google.android.apps.chromecast.app | grep versionCode`) — если Play Store обновил, повторить шаг декомпиляции (раздел 4 п.5) для нового билда.
3. Спаунить приложение **через Frida сразу с флагом `-f`** (не attach к уже запущенному), чтобы гарантированно поймать процесс с самого начала и не потерять хук при случайном перезапуске:
   ```bash
   frida-old-venv/bin/frida -U -l runtime/frida/locale-hook.js -f com.google.android.apps.chromecast.app
   ```
4. **Держать эту команду в foreground/следить за её выводом активно**, не полагаться на фоновые уведомления — при любом признаке "Attaching..."/session end немедленно проверять реальный PID процесса (`adb shell su -c pidof ...`) и, если не совпадает, переприсоединяться заново.
5. Дойти до экрана выбора языка **не выходя из приложения и не давая ему уйти в фон** между установкой хука и проверкой.
6. Если после этого русский всё ещё не появится — следующая гипотеза для проверки: возможно, UI строит список ОДИН РАЗ при первом входе в конкретный Fragment/Activity и кеширует его (в этом случае нужно поймать хук ДО первого захода на этот экран, т.е. спаунить заново и НЕ заходить в setup до подтверждения "hook installed" в логе Frida).

### Новые знания

- **Обфускация R8/Proguard в этом приложении нестабильна между билдами** — нельзя полагаться на конкретные имена классов/методов из одной декомпиляции для другой версии APK. Каждый раз, когда меняется установленная версия (в т.ч. через простое обновление Play Store), нужно передекомпилировать актуальный `base.apk` заново.
- В процессе Google-приложения через Chimera сосуществуют **классы из нескольких classloader'ов** (сам APK + динамически подгруженные модули GMS) — фильтрация по `loader.toString()` обязательна, иначе легко попасть на "чужой" класс с совпадающим коротким именем.
- Frida `-p` (attach к уже работающему процессу) хрупок при длинных пользовательских сессиях — если приложение уйдёт в фон/перезапустится, хук теряется молча, и нет автоматического способа узнать об этом кроме явной проверки PID.

## 7. Рекомендации для следующей сессии

В порядке убывания перспективности:

1. **Довести до конца подход №4** (Frida runtime-хук `knf.v`, раздел 5) — технически почти готов, просто нужно аккуратно поймать актуальный процесс и не дать ему уйти из-под хука до проверки экрана. Наименее инвазивный вариант (не трогает подпись, не требует сетевого MITM).
2. Если подход №4 всё же не даст результата даже с рабочим хуком в списке UI (т.е. `ru-RU` появится в списке, но после выбора всё равно не сохранится/не заработает голосовое распознавание) — это будет означать, что даже клиентского UI-разблокирования недостаточно, и упираемся в тот самый "трёхслойный" барьер из раздела 0 (Assistant Settings profile / Voice Match voiceprint locale) — тогда, вероятно, единственный оставшийся путь — LSPosed/Xposed signature spoofing (позволит патчить APK **и** сохранить доверие GMS), что открывает возможность полноценно патчить/логировать саму GMS, а не только гадать через её публичные интерфейсы.
3. Подход №1 (чистый MITM) можно ещё раз попробовать оживить, если добавить в `relocalize.py` **verbose-логирование всех путей** (не только совпадений) к allowlist-доменам — это даст полную картину, какие эндпоинты реально вызываются при привязке, и, возможно, найдётся не-строковый (protobuf enum) механизм передачи локали, который текущая побайтовая замена принципиально не видит.
