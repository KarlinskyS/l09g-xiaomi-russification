# Архитектура проекта `google-home-russian`

Цель: полностью автоматизированное поднятие MITM-инфраструктуры для перехвата/модификации трафика Google Home устройства (сценарий: обход региональных ограничений через локальный проксирующий слой). MITM-цепочка (mitmproxy + доверенный CA) считается уже рабочей и берётся за основу нижнего уровня — этот документ описывает **оркестрацию вокруг неё**, а не сам перехват.

---

## 1. Принципы архитектуры

- **Одна точка входа** — `bootstrap.sh`. Пользователь не выполняет ручных шагов кроме случаев, требующих физического действия (установка сертификата на устройство, подключение к Wi-Fi).
- **Идемпотентность** — повторный запуск `bootstrap.sh` не ломает уже настроенное окружение, а проверяет и докручивает недостающее.
- **Стадийность (pipeline)** — каждая стадия изолирована, имеет свой статус (`pending / running / ok / failed / skipped`), пишет в общий журнал состояния.
- **Декларативная конфигурация** — одно место (`config/`), откуда берутся все параметры: диапазон адресов устройства, порт прокси, домены для перехвата, пути экспорта.
- **Наблюдаемость по умолчанию** — каждая стадия обязана логировать вход/выход/результат, ничего не делается «молча».
- **Восстановимость** — любая стадия может быть перезапущена отдельно (`bootstrap.sh --stage=<name>`), не только целиком.

---

## 2. Структура репозитория

```
google-home-russian/
├── bootstrap.sh                  # единственная точка входа
├── config/
│   ├── environment.yaml          # версии python/mitmproxy, пути
│   ├── network.yaml              # диапазон устройства, порт прокси, whitelisted-домены
│   └── logging.yaml              # уровни, ротация, форматы
│
├── stages/                       # каждая стадия — отдельный самодостаточный модуль
│   ├── 00-preflight/             # проверка ОС, прав, свободных портов, интернета
│   ├── 10-python-env/            # подготовка изолированного python-окружения
│   ├── 20-mitmproxy/             # установка и версия-пиннинг mitmproxy
│   ├── 30-certificates/          # генерация/переиспользование CA, экспорт форматов
│   ├── 40-proxy-runtime/         # запуск/остановка/супервизия процесса mitmproxy
│   ├── 50-device-instructions/   # генерация пошаговой инструкции под ОС устройства/хоста
│   ├── 60-verification/          # автоматическая проверка готовности всей цепочки
│   └── 70-export/                # упаковка логов, конфигов, сертификатов, отчёта
│
├── runtime/                      # генерируется в процессе работы, в git не попадает
│   ├── state.json                # машина состояний по стадиям
│   ├── venv/
│   ├── certs/
│   └── logs/
│
├── exports/                      # финальные артефакты для передачи/архивации
│
├── docs/
│   └── device-setup/             # шаблоны инструкций (Android/iOS/router-level)
│
└── tests/
    └── verification-checks/      # спецификации проверок, используемые stage 60
```

## 3. Оркестратор `bootstrap.sh`

Отвечает только за **последовательность и контроль**, никакой бизнес-логики внутри самого файла.

Обязанности:
1. Прочитать `config/*.yaml`, провалидировать схему.
2. Прочитать/создать `runtime/state.json`.
3. Выполнить стадии `00 → 70` по порядку, пропуская те, что уже в статусе `ok` (если не передан `--force`).
4. После каждой стадии — записать статус, длительность, hash использованных конфигов (для инвалидации кэша при изменении конфигурации).
5. При падении стадии — остановиться, вывести диагностический summary, предложить точку перезапуска.
6. В конце — вывести человекочитаемый итоговый отчёт (что настроено, что требует ручного действия, где лежит экспорт).

Флаги (концептуально, без реализации):
- `--stage=<name>` — точечный перезапуск одной стадии.
- `--force` — игнорировать кэш состояния.
- `--dry-run` — показать план без выполнения.
- `--verify-only` — прогнать только стадию 60.
- `--export-only` — прогнать только стадию 70.

## 4. Стадии — назначение и границы ответственности

### 00 · Preflight
Проверяет: ОС/архитектуру, права (нужен ли sudo для сети/сертификатов), занятость нужных портов, наличие базовых системных зависимостей (curl, openssl), доступность интернета. Результат — machine-readable отчёт о совместимости среды, блокирующий дальнейшие стадии при критичных несоответствиях.

### 10 · Python-окружение
Проверяет требуемую версию Python, создаёт изолированное окружение (venv/аналог), фиксирует набор зависимостей по lock-файлу. Не устанавливает mitmproxy напрямую — только базовый слой интерпретатора и пакетного менеджера.

### 20 · mitmproxy
Устанавливает mitmproxy строго в изолированное окружение из стадии 10, пиннингует версию (совместимость с конфигом перехвата), проверяет корректность установки через вызов версии/справки. Отдельно фиксирует путь к бинарю/модулю для использования стадией 40.

### 30 · Сертификаты
- Проверяет, существует ли уже локальный CA mitmproxy (переиспользование вместо пересоздания).
- При отсутствии — инициирует его создание через сам mitmproxy (полагаясь на встроенный механизм, а не на кастомную криптографию).
- Экспортирует сертификат в форматы, нужные под целевые устройства/платформы (например, формат для мобильного профиля, формат для роутера/хоста).
- Фиксирует fingerprint сертификата в state — используется стадией 60 для проверки, что на устройстве установлен именно этот CA, а не устаревший.

### 40 · Proxy runtime
Отвечает за жизненный цикл процесса mitmproxy: старт, остановка, health-статус, супервизия (перезапуск при падении в рамках сессии). Конфигурация перехвата (домены, правила модификации) подключается как внешний, версионируемый артефакт — сама стадия не содержит логики перехвата, только управляет процессом.

### 50 · Device instructions
Генерирует **персонализированную** пошаговую инструкцию (не статичный текст), подставляя актуальные данные из runtime: IP/порт прокси хоста, текущий fingerprint сертификата, конкретные шаги под определяемую платформу устройства. Формат — человекочитаемый документ (markdown/HTML), кладётся в `docs/device-setup/generated/`. Эта стадия — единственное место, где явно ожидается ручное действие пользователя (физическая установка сертификата/настройка прокси на устройстве), поэтому она должна явно приостанавливать пайплайн и запрашивать подтверждение «шаги выполнены» перед переходом к 60.

### 60 · Verification
Автоматическая сквозная проверка готовности всей цепочки без участия человека, за исключением подтверждения из стадии 50. Проверяет по уровням:
- сетевой уровень — устройство достижимо, прокси слушает порт;
- TLS-уровень — устройство доверяет CA (проверка через тестовый запрос/handshake);
- уровень перехвата — трафик действительно проходит через mitmproxy (по логам/счётчикам сессий), а не идёт в обход.

Результат — явный статус готовности по каждому уровню, а не общий «ок/не ок» — чтобы диагностика проблемы была прицельной.

### 70 · Export
Формирует итоговый архив в `exports/` с временной меткой:
- копия конфигурации, использованной в запуске;
- сертификаты (без приватного ключа CA в «горячем» экспорте — приватный ключ остаётся только в `runtime/certs`, экспортируется отдельно и опционально, под явный флаг);
- логи текущей сессии;
- отчёт верификации (стадия 60) в структурированном виде;
- манифест с версиями всех компонентов (python, mitmproxy, конфиги) — для воспроизводимости и последующей поддержки/дебага.

## 5. Логирование (сквозной слой, не отдельная стадия)

- Единый структурированный формат логов (уровень, стадия-источник, timestamp, machine-readable payload) — используется всеми стадиями, конфигурируется из `config/logging.yaml`.
- Разделение потоков: **оркестраторный лог** (последовательность стадий, статусы) отдельно от **runtime-лога mitmproxy** (сетевые события) — чтобы диагностика инфраструктуры не смешивалась с диагностикой трафика.
- Ротация и ограничение объёма — конфигурируемые, чтобы длительные сессии перехвата не разрастили логи бесконтрольно.
- Обязательное правило: секреты (приватный ключ CA, токены, если появятся) никогда не пишутся в лог — только их fingerprint/идентификатор.

---

## 6. Модель состояния и восстановления

`runtime/state.json` — единственный источник правды о прогрессе:
- статус каждой стадии + hash использованной конфигурации на момент выполнения;
- при изменении конфигурации соответствующая стадия и все зависящие от неё автоматически помечаются `stale` и требуют перезапуска;
- при сбое — стадия остаётся `failed` с привязанным диагностическим сообщением, оркестратор не пытается «угадывать» восстановление сам, а даёт пользователю точную команду для точечного перезапуска.

---

## 7. Границы безопасности

- Приватный ключ CA никогда не покидает `runtime/certs` без явного флага экспорта — потому что доверенный локальный CA, утёкший наружу, эквивалентен возможности MITM для кого угодно, кто его получит.
- Инструкции для устройства (стадия 50) явно предупреждают о том, что установленный CA даёт доверие только для целей этого проекта, и должны включать шаг/напоминание об отзыве/удалении сертификата с устройства, если перехват больше не нужен.
- Конфигурация домeнов перехвата — allowlist, не catch-all: стадия 40 должна проксировать только заявленные в `config/network.yaml` домены, чтобы не перехватывать весь трафик устройства без необходимости.
