## Dropbear: что в прошивке и почему порта нет

### Ошибка интерпретации флага `-G`

В **стандартном** Dropbear:

- `-B` — разрешить вход с пустым паролем;
- `-G <group>` — ограничить вход членами указанной группы.

Источник: документация NCSC / upstream Dropbear. Строка init `sshd -G -r /etc/rsa_host_key -F` **сама по себе не доказывает** passwordless login. Это была ошибка предыдущего чтения help-текста.

### Что в **этом** бинарнике 1.52.56

Файл: `/tmp/l09g-ota-15256/system/usr/bin/dropbearmulti` (`sshd` → тот же multi-binary). ELF32 ARM EABI5 PIE, Thumb, `e_entry 0x2641`, баннер `SSH-2.0-dropbear_2016.74`. Хост-ключ: `/system/etc/rsa_host_key`.

Это не стоковый Dropbear 2016.74. Обёртка Google/Xiaomi:

1. Диспетчер по basename (`0x162c8`): `strcmp` с `sshd` → переход `b.w` на обёртку `0x923c`.
2. Обёртка **до** `dropbear_main` (`0x8720`) и **до** `listen()` читает `ro.product.release.track` через `property_get`, сравнивает 15 байт с `stable-channel`, при совпадении пишет в лог `disabled on stable-channel\n` и делает `exit(1)`.
3. Разбор argv сервера — ручной, не `getopt`. Таблица от `'B'`, TBH на `0x8818`. Ветки `'B'` и `'G'` обе прыгают на `0x8888` и ставят `allowblankpass=1` (`str.w fp, [r1, #0x70]`). Help этого бинарника тоже подписывает оба флага как «Allow blank password logins».
4. Единственный libc `getopt` в файле — **клиентский**, optstring `dfl:prtvBCc:i:P:q1246S:o:F:` по адресу `0x13d36`. Сравнения с `'G'` (`0x47`) в клиентском парсере нет.

`build.prop` этой OTA: `ro.product.release.track=stable-channel`, `ro.build.type=user`, `ro.build.tags=test-keys`. Init запускает `sshd -G -r /etc/rsa_host_key -F` как oneshot при загрузке — и обёртка сразу завершается.

### Почему в полном TCP-скане не было SSH

Ранее на доноре (Ванная, `.118`) полный `nmap -p-` нашёл **восемь** открытых TCP: `8008`, `8009`, `8012`, `8443`, `9000`, `10001`, `10007`, `10101`. SSH среди них не было.

Это согласуется с кодом: процесс стартует, видит `stable-channel`, выходит, сокет не слушает. Не «закрытый порт с отказ в аутентификации», а отсутствие слушателя.

## Cast getUserMedia

Hermes нужен поток с микрофонов. Если на пользовательском Custom Receiver в 1.52.56 реально включён доступ к медиа, функция возможна без root. Если доступ выключен и SSH недоступен, дальше — отдельная уязвимость сетевого сервиса или физический доступ.

### Что в прошивке 1.52.56

Chromium на Cast даёт микрофон, если выполняется **хотя бы одно**:

- глобальный feature `kAllowUserMediaAccess` (`allow_user_media_access`), в AOSP/Chromium по умолчанию **выключен**;
- либо per-app флаг `allow_media_access_` у конкретного WebView (в Cast Core / `ApplicationConfig`, обычно first-party вроде Duo/Meet).

Наблюдения по дампу:

- Имя фичи в `chrome/cast_shell` есть. В `chrome/process.json` из `--enable-features` указано только `AudioWorkletRealtimeThread`. Глобальный media-access флаг не включён.
- `start_cast_shell.sh` передаёт `--audio-input-mic-sensitivity=-26`, `--enable-voice-trigger=false`, `--disable-speech-api`. Флага media-access нет.
- В бинарнике есть `cast_web_view_default.cc` и суффикс лога `: media access is disabled.`
- ALSA: `pcm.!default` capture = встроенные микрофоны `hw:AMLAUGESOUND,3`, 16 кГц, 2 канала. `pcm.aux_in` — линейный вход `hw:AMLAUGESOUND,2`. В `process.json` `local-audio-input-device-id` по умолчанию `plug:aux_in` (это путь ассистента/линейного входа, не доказательство того, что getUserMedia ходит туда же).
- Рядом в бинарнике есть и `alsa_audio_input.cc`, и `capture_service_dummy.cc`. Наличие ALSA-захвата в прошивке не равно разрешению веб-приложению.

Отсутствие глобального флага **не исключает** per-app grant. Оснований ждать его на произвольном Custom Receiver нет. Это измеряется только живым запуском.

### Эксперимент из четырёх результатов

Живой запуск ограничен четырьмя ответами, больше ничего не оптимизировать, пока нет (1):

1. Стартует ли наш HTTPS Custom Receiver на L09G.
2. Есть ли `navigator.mediaDevices`.
3. Что возвращает `getUserMedia({audio:true, video:false})` — поток или отказ (имя ошибки / constraint).
4. Если поток есть: есть ли реальный сигнал со встроенных микрофонов (RMS за 10×100 мс, порог `peak > 1e-4` → `signal`, иначе `silence-or-zeros`).

Диагностика лежит в [`tools/cast-mic-probe/`](../tools/cast-mic-probe/): страница Receiver API v2 шлёт JSON в namespace `urn:x-cast:hermes.micprobe`; sender запускается в контейнере netguard и не трогает громкость. После ответа или таймаута делает `STOP`.

Если (1)–(3) отвалятся из‑за выключенного media access, дальше крутить generic Custom Receiver бессмысленно: нужен отдельный механизм разрешения.

### Два последовательных критерия успеха

Рабочий микрофон в сессии **не** означает, что Hermes может постоянно слушать «Гермес». Custom Receiver живёт внутри Cast-сессии.

1. **Сначала** — PCM через штатный Cast (четыре результата выше).
2. **Потом** — отдельный план: автозапуск, удержание сессии, восстановление после reboot и после Assistant. Без телефона и без ручного relaunch.

Критерий 2 не начинать, пока критерий 1 не измерен.

### Что блокирует запуск прямо сейчас

- Неопубликованный Custom Receiver App ID в [Cast Developer Console](https://cast.google.com/publish/) (на аккаунт владельца, не Default Media Receiver).
- Публичный HTTPS с валидным сертификатом, куда консоль прописывает URL приёмника. Sender URL не подставляет.

Пока этого нет, страница и sender в репозитории — подготовка, не проведённый опыт.
